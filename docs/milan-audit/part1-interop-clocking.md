### Violations and partials, in priority order

**1. 4.3.1.1 — Talker PAAD is NOT grandmaster capable (VIOLATES — the single most important finding).**
Exact spec text: *"As per [802.1BA, Clause 6.7.2], a Talker PAAD shall be capable of operating as a gPTP grandmaster."* Supporting clause 4.2.6.2.1: *"If a PAAD is Grandmaster Capable the default priority1 value defined in [802.1AS, Clause 8.6.2.1] shall be 248 (Other Time-Aware System). Note: Section 4.3.1.1 defines that all Talker PAADs have to be Grandmaster Capable."*

What "Grandmaster Capable" requires: the gPTP port must be able to assume the Master role when BTCA (802.1AS Clause 10.3) selects it — i.e. transmit Announce messages (default 1 s interval) carrying its own clockQuality/priority vectors, transmit Sync + Follow_Up (default 125 ms) as the time source, participate in BTCA as a candidate (not only consume Announce as a slave), and when GM-capable advertise `priority1 = 248` (not 255). The PTP_INSTANCE descriptor must carry the `GRANDMASTER_CAPABLE` flag (per 7.5.4).

What our `avb-gptp` does today: it is **architecturally slave-only**. The crate header declares *"sans-IO, slave-only IEEE 802.1AS time-aware end station"* and *"Announce/Sync/Follow Up are decode-only"* (`/Users/dexter/AVB-Audio/crates/avb-gptp/src/lib.rs:3-6`). `PortState` has only `Listening` and `Slave` — there is no `Master` (`/Users/dexter/AVB-Audio/crates/avb-gptp/src/port.rs:62-66`), and the module doc states *"no Announce, Sync or Follow_Up transmit path: it can never become master"* (`.../port.rs:7-11`). `PRIORITY1 = 255` with the comment *"It never appears on the wire: we send no Announce (design §7.1, user decision)"* (`.../lib.rs:43-45`), and the AVB_INTERFACE descriptor advertises `priority1: 255` precisely to *"keep us from ever winning BMCA"* (`/Users/dexter/AVB-Audio/crates/avb-avdecc/src/entity/talker.rs:617-620`). `interface_flags` set only `GPTP_SUPPORTED | SRP_SUPPORTED`.

What we do instead: as a slave, we accept Announce (`rx_announce`), pick the advertised GM, slave the servo to its Sync/Follow_Up, and re-advertise ADP with the selected GM identity — correct listener behaviour, but it can never source time if no external GM exists.

Code change needed: add a Master role to the port state machine, an Announce TX path (default 1 s, Table 4.1 tolerances), a Sync/Follow_Up TX path (default 125 ms), a full BTCA that treats our own clock as a candidate dataset, set GM-capable `priority1 = 248` / `priority2 = 248` / `clockClass`/`clockAccuracy`/`variance` for the data set, set `GRANDMASTER_CAPABLE` on the PTP_INSTANCE, and flip the AVB_INTERFACE `priority1` to 248. **Size: large** (new transmit state machine, BTCA, Sync/FU timestamping on TX, and the descriptor changes; interacts with the servo, which currently has no "disciplining our own oscillator as GM" mode). Note this was a deliberate `user decision` per the code comments, so it is a scope/architecture question for the owner, not a bug.

**2. 4.2.6.2.1 — priority1 is 255, not 248 (VIOLATES, coupled to #1).**
Spec: GM-capable default priority1 **shall be 248**. We hardcode 255 in two places (`/Users/dexter/AVB-Audio/crates/avb-gptp/src/lib.rs:45`; `/Users/dexter/AVB-Audio/crates/avb-avdecc/src/entity/talker.rs:620`). Change: set to 248 as part of making the device GM-capable. **Size: small** on its own, but meaningless without #1 (255 is the correct value *only* for a device that is deliberately not GM-capable, which itself violates 4.3.1.1).

**3. 4.2.6.2.5 — no cease-Pdelay on multiple responders (VIOLATES).**
Spec: on >1 responder clock identity across three successive Pdelay_Reqs, the PAAD *"shall cease Pdelay Request transmission until"* link/portEnabled/pttPortEnabled toggles or 5 minutes elapse, then resume. We detect the multi-responder condition (`multiple_responders` counter, `multi_responder()` lookback over 3 exchanges) and let it drive asCapable → false (`/Users/dexter/AVB-Audio/crates/avb-gptp/src/pdelay.rs:255-262,311-313`), but `poll_initiator` keeps sending Pdelay_Req on the normal interval regardless (`/Users/dexter/AVB-Audio/crates/avb-gptp/src/port.rs:600-619`) — there is no suppression state or 5-minute timer. Change: add a "pdelay suppressed" state entered when `multi_responder()` is true over 3 successive requests, gating `poll_initiator`, cleared on link/port toggle or a 5-minute timer. **Size: medium.**

**4. 4.3.5.2 — Talker never sets the AVTP tu bit (VIOLATES).**
Spec: *"A Talker PAAD shall set the AVTP 'tu' bit as described in [AVTP, 4.4.4.7]."* The AAF talker hardcodes `tu: false` for every PDU (`/Users/dexter/AVB-Audio/crates/avb-avtp/src/talker.rs:121`); nothing wires the gPTP sync-uncertain state into it. The tu bit must be set true while the Talker's gPTP time is uncertain (not yet locked / GM change / holdover) and cleared when locked. Change: plumb the gPTP servo/lock state (e.g. `servo_state`, `as_capable`, GM-change edges) into the talker and set `tu` accordingly per PDU. **Size: medium** (crosses the gPTP↔audio boundary that the code elsewhere notes is not currently plumbed, e.g. `media_ppm_vs_gptp` passes 0.0 — `/Users/dexter/AVB-Audio/crates/avb-mediaclock/src/lib.rs:48-56`).

**5. 4.2.6.1.1 — neighborPropDelayThresh has no copper/fiber handling (PARTIAL).**
Spec: copper default **800 ns**; fiber **disabled by default**. We hardcode a single `NEIGHBOR_PROP_DELAY_THRESH_NS = 800.0` applied unconditionally (`/Users/dexter/AVB-Audio/crates/avb-gptp/src/pdelay.rs:20-21,300`). For the I210 copper target this value is correct, so copper complies; but there is no port-media type input and no path to disable the threshold on fiber. The const comment even flags the standard clause as `*(verify)*`. Change: make the threshold configurable by port media type and allow disabling (None) on fiber. **Size: small** (the I210 product is copper-only, so this is a conformance-completeness gap, not a functional bug for this hardware).

**6. 4.2.6.2.4 — asCapable not bounded to the 2..5 Pdelay-response window (PARTIAL).**
Spec: asCapable TRUE after **no less than 2 and no more than 5** successful Pdelay Response + Response_Follow_Up exchanges. Our asCapable requires a valid NRR (≥2 exchanges) plus delay/loss/multi conditions (`/Users/dexter/AVB-Audio/crates/avb-gptp/src/pdelay.rs:290-322`), which satisfies the "no less than 2" floor implicitly, but there is no explicit success counter and no "no more than 5" upper bound guaranteeing asCapable is reached within 5 good exchanges. Change: add a successful-exchange counter and assert asCapable within [2,5]. **Size: small.**

**7. 4.4.2.3 — tu bit not used to free-wheel the listener media clock (PARTIAL; non-binding "should").**
Spec (should): after detecting tu reset, continue free-wheeling the media clock. We decode and count the tu bit (`/Users/dexter/AVB-Audio/crates/avb-avtp/src/common.rs:62,81`; counter `timestamp_uncertain` in `/Users/dexter/AVB-Audio/crates/avb-daemon/src/audio.rs:32`) but it does not drive media-clock free-wheel behaviour. Non-binding, but worth noting for interop with a GM change. **Size: small-medium.**

**8. 4.4.2.1 — 2.126 ms listener buffering not directly proven (PARTIAL).**
Spec: Listener shall buffer ≥ 2.126 ms. The code reasons about this correctly (talker emits the 2 ms max offset; listener accept-bound `early_bound = max(ta_latency,2ms)+125µs` ≥ 2.125 ms — `/Users/dexter/AVB-Audio/crates/avb-mediaclock/src/placement.rs:9-18`, `/Users/dexter/AVB-Audio/crates/avb-daemon/src/stack.rs:3089-3105`), and the ring capacity is `RING_SPAN_S = 1.25 s` (far exceeds 2.126 ms). But "support buffering of received samples for at least 2.126 ms" is an accept/hold-depth guarantee I did not find asserted as a single ≥2.126 ms bound. Likely COMPLIES in practice via the 1.25 s ring, but marked PARTIAL because no single line states the 2.126 ms figure as the enforced minimum. **Size: small** (add an assertion/test).

### Notes

- **The dominant finding (4.3.1.1) is a deliberate design choice, not an accident.** Multiple code comments cite a *"user decision"* / *"design §7.1"* / *"design §13.3"* to be slave-only. Milan nonetheless makes grandmaster capability mandatory for any Talker PAAD. If the product is to certify as a Talker PAAD, this is a large architectural addition (Master role + Announce/Sync TX + full BTCA + GM-capable dataset + descriptor flags). If the owner intends to ship as Listener-only, that changes the applicable requirement set and should be decided explicitly — several Talker rows above would then move to NOT APPLICABLE.
- **Scope boundaries honored:** 4.2.7.x (MRP/MSRP/MVRP), 4.3.2/4.3.3.x (MVRP/MSRP/Tspec), 4.3.4 (CBS), 4.4.1 (MVRP), and 7.6.1.x (Media Clock Reference Priority commands via §5.4.4) depend on crates/sections outside this part (avb-srp, §5 connection management). I marked them NOT APPLICABLE *to this part* rather than judging compliance I could not verify in my ranges — the SRP/connection auditor must cover them.
- **4.3.4 CBS** is genuinely ambiguous for a macOS end station: §4.3.4 requires the Talker to implement the Credit-Based Shaper per 802.1Q Cl.34. On a software end station the CBS is typically enforced by the NIC/driver TX scheduling (the I210 has hardware launch-time/credit shaping) rather than by application code; I found no CBS logic in-scope and could not confirm the I210 datapath configures it. This needs a dedicated check against avb-dext/NIC config — flagging as a known gap, not scored.
- **CRF Media Clock Input/Output (7.2.2/7.2.3)** is subtle: our listener binds and locks to the 16R's `Send CRF`/`Return CRF` stream (STREAM_INPUT_0 is CRF at 48000 — `/Users/dexter/AVB-Audio/crates/avb-avdecc/src/aem/desc.rs:896`), so a CRF *input* exists on the listener side. Whether the device, as an *AAF Media Talker*, exposes the required CRF Media Clock Input, and whether a device "capable of synchronizing to an external clock source" exposes a CRF Media Clock *Output*, is undetermined — our talker's CLOCK_SOURCE is INTERNAL (Mac clock) only, which may make 7.2.3's "capable of synchronizing to an external clock source" conditional false. A connection/descriptor auditor should confirm the CRF descriptor set against a live `GET_STREAM_INFO`.
- **Negative Pdelay (4.2.6.2.7) is the one gPTP clause we cleanly pass**: the asCapable rule has no lower delay bound, so a −80..0 ns compensated delay does not trip `delay_above_thresh`. There is also no explicit floor rejecting delays below −80 ns, which is fine for this clause but could let a grossly-negative (broken) delay through — out of scope here but worth a glance.
- **Standard-clause `*(verify)*` markers** in `pdelay.rs` (lines 20, 22, 24, 30) mean the implementer themselves flagged the 802.1AS default values (800 ns, allowedLostResponses=3, gPtpCapableReceiptTimeout=9) as unverified against the base standard. The *Milan* values I checked (800 ns copper, 3× receipt-timeout multiplier) match the spec; the underlying 802.1AS citations should still be verified by someone with that document.
- I read every line in both assigned ranges (1048–1454 and 6541–6812) and every cited code line. No MCP servers were needed for this task; the only unavailable server reported this session was `@kirocrew-computer` (not configured), which is irrelevant to a read-only code audit.
